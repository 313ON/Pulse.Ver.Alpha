# معماری محصول و تجربه کاربر PULSE

## وضعیت و دامنه

این سند پایه محصول/UX برای تبدیل PULSE از یک ابزار داخلی مهندسی‌محور به محصولی قابل استفاده برای کاربران با سواد دیجیتال متفاوت است. این مرحله قرارداد معماری و زبان محصول را مشخص می‌کند؛ بازطراحی بصری یا تغییر قواعد کسب‌وکار در دامنه آن نیست.

منبع حقیقت فعلی کد است: پوسته `PulseShell`، ناوبری `CommandSidebar`، جستجوی `CommandHeader`، مسیرهای Next.js، سرویس‌های application، مدل دامنه و مجوزهای `auth.ts`. مدل اصلی حفظ می‌شود:

`برنامه → هدف → هدف جزئی → فعالیت → اقدام → شاخص`

واحد، سمت، شخص، ریسک، وابستگی، بازبینی ماهانه، چرخه برنامه، شناسه‌های PULSE و شناسه‌های منبع خارجی در همان مدل باقی می‌مانند.

## اصل محصول

**کاربر نیت خود را بیان می‌کند؛ PULSE پیچیدگی دامنه را مدیریت می‌کند.**

کاربر می‌گوید «برای واحدم یک هدف ثبت کنم». رابط کاربر اطلاعات لازم را مرحله‌به‌مرحله می‌گیرد و application service آن را به عملیات معتبر دامنه تبدیل می‌کند. کاربر نباید parent ID، foreign key، شناسه PULSE، رابطه داخلی یا اصطلاحات پیاده‌سازی را وارد کند. شناسه‌های داخلی همیشه خودکار و غیرقابل ویرایش‌اند.

## قرارداد لایه‌ها

Presentation فقط intent و ورودی خوانا را جمع‌آوری می‌کند. Application service آن intent را به command/query تبدیل می‌کند. Domain rules مالک اعتبارسنجی، وضعیت و روابط‌اند. Infrastructure مالک persistence، import، export و audit است. هیچ فرم یا route نباید مستقیماً به SQLite یا repository داخلی دست بزند.

## سطح‌های آشکارسازی

- **ساده:** کار بعدی، وضعیت، مسئولیت، مهلت، توضیح کوتاه و کمک درون‌زمینه.
- **حرفه‌ای:** اهداف جزئی، فعالیت‌ها، شاخص‌ها، پیشرفت، ریسک، وابستگی و گزارش‌دهی.
- **پیشرفته:** شناسه فنی، منبع و provenance، audit، روابط کامل، وضعیت import و diagnostics.

هر سه سطح روی همان domain model و application boundary کار می‌کنند؛ سطح بالاتر داده معتبر تازه‌ای ایجاد نمی‌کند.

## تعریف موفقیت

پس از ورود، کاربر باید در یک صفحه بفهمد چه کاری از او انتظار می‌رود، بتواند نخستین کار مفید را بدون شناخت معماری انجام دهد، و در خطا بداند چه اتفاقی افتاده و قدم بعدی چیست.

## اصول تصمیم‌گیری

1. نیت قبل از موجودیت؛ مسیر «ایجاد هدف» قبل از نمایش فرم خام Goal.
2. راهنمایی مرحله‌ای قبل از آزادی کامل؛ wizard برای ایجاد و import.
3. وضعیت با متن، آیکون و الگوی قابل دسترس؛ نه فقط رنگ.
4. داده تاریخی و provenance هرگز با latest/current پر نمی‌شود.
5. عملیات مخرب یا برگشت‌ناپذیر حداقل و با recovery روشن است.
6. نقش و scope فعلی حفظ می‌شود؛ UX آن را ساده می‌کند، نه اینکه دور بزند.

## موارد خارج از این مرحله

تغییر schema، تغییر identity، تغییر قواعد دامنه، multi-tenancy اجرایی، بازطراحی CSS و پیاده‌سازی AI انجام نمی‌شود.
